# 什么算 Bug

**在已声明支持的环境中，实际行为违反已接受的玩法约定、用户可合理预期的交互或工程不变量，就是需要调查的缺陷。** 不以“旧版也这样”“没有崩溃”“测试全部通过”作为自动免责理由；也不把个人偏好直接当作产品错误。

## 判定依据

优先核对当前需求和模块规格，再参考手册、配方展示、目标版本原生语义、官方 API 契约及旧版实际行为。来源冲突时记录冲突：文档可能过期、反编译可能失真、移植规格可能有意改变旧机制。不要暗自选最方便实现的一项。

| 分类 | 例子 | 处理 |
| --- | --- | --- |
| 崩溃与数据损坏 | 普通操作抛异常、读档丢库存、无提示地清除未知数据 | 确认原因与保存边界，优先修复并做重载回归 |
| 逻辑与守恒缺陷 | 未付款领取结果、拒收后吞物、同次回调重复掉落 | 检查事务、幂等性、容量和所有进出路径 |
| 权限/侧别错误 | 客户端可决定产物、保护事件被绕过、旁观者改变世界 | 由权威逻辑验证请求与权限，验证拒绝路径 |
| 可用性与表现缺陷 | GUI 点不到、默认配置无法推进、模型缺失、信息与实际配方不同 | 真实操作与画面复现；不能仅检查数据字段 |
| 兼容性缺陷 | 声明可选的依赖缺失却崩溃、承诺支持的组合失效 | 最小安装/完整组合对照，核对精确版本与 API |
| 性能缺陷 | 常规规模下每帧重建全表、查询造成卡顿或无界内存增长 | 用固定场景和 profiler 建立证据，区分工具开销 |
| 明确设计行为 | 规格约定的成本、概率、限制，实际符合约定 | 解释依据；体验不佳可另列建议 |
| 功能建议/平衡调整 | 新增配方、改变难度或产量 | 作为需求，不混入 Bug 修复授权 |
| 未支持环境/信息不足 | 未承诺的版本组合，只有一句“不能用” | 记录缺失条件，仍可调查；不直接写“已修复”或“不是 Bug” |

同一现象可以有多个原因，例如“物品闪现”可能来自逻辑停步、网络追踪、客户端整体卡顿或渲染剔除。先做区分，再确定修复位置。

## 旧版行为的处理

默认采用可玩性优先的移植目标。崩溃、复制、吞物、无效数据、明显笔误和不合理的实现限制应修复并登记差异；不能为了逐行为一致继续保留这些缺陷。与进程、成本或策略有关的有争议行为先按规格归类，不能借“修 Bug”擅自全面增强或削弱玩法。

若项目要求严格保真，必须在 PROJECT-CONFIG 指明范围及已接受的例外。保存格式、ID 别名等兼容保留与保留旧漏洞是两回事；现代重写不能借修 Bug 删除兼容承诺。

## 状态与严重度分开

问题状态建议为 `reported → investigating → confirmed → fixed-unverified → verified → delivered`，也可为 `not-reproduced`、`needs-info`、`by-design`、`deferred-by-user`。只有实际运行且符合预期才写 `verified`；静态审查可确认代码层错误，但仍标记运行验证未完成。

严重度按影响评估：数据损坏/复制/广泛崩溃优先，主流程阻断次之，局部错误再后，轻微表现问题最后。优先级不等于复现程度。重复报告归并到同一问题并保留不同触发条件，不按消息数量统计 Bug 数。

使用 [Bug 模板](Templates/BUG-REPORT.md) 保存预期、实际、来源依据、复现、根因、修复与回归。未复现只能说明本轮给定条件下未出现，不能排除用户现场。
