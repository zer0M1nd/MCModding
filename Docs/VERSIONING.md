# 默认版本号协议

本模板沿用一套 **可由维护者修改的自定义协议**，不是标准 SemVer。用户可以要求改用其他规则；变更程序见末节。版本语义与发布授权分开，确定版本号不自动授权外部上传。

## 格式与含义

使用 `w.x.y` 或 `w.x.y.z`，每段为无前导零的非负整数；存在的 `z` 必须大于 0，`z=0` 必须省略。

| 段 | 定义 |
| --- | --- |
| `w` | 代数，偏象征意义。`w=0` 尚未正式发行，`w>0` 已正式发行；具体代数由用户决定 |
| `x` | 重大更新。可能使旧存档无法打开或旧配置无法复用的累计改动，在稳定发布时必须提升 x；用户也可因重要玩法等理由主动提升 |
| `y` | 稳定更新。经过与影响范围相匹配的充分测试，可以是 Bug 修复，也可以仅将已测试候选晋级 |
| `z` | 开发迭代编号。Agent 日常自动开发默认只递增 z，不代表内容量小，也不保证兼容 |

三段是稳定版，四段是开发/不稳定版。发行阶段与稳定性独立：`0.2.3` 可以稳定，`1.2.3.1` 仍是不稳定版。初始模板没有任何已发布版本；例如 `0.1.0.1` 只能作为未来首个开发候选的选择，不能据此虚构 `0.1.0` 已通过验收。

## 比较与递增

- 按整数逐段比较；三段在比较时补一个零，但序列化必须省略它。禁止字符串比较，例如 `0.2.10` 大于 `0.2.9`。
- 各 Mod 独立编号。每个新发布版本大于本 Mod 所有先前已发布版本；不得复用同一版本发布不同内容。
- 从稳定版进入开发时，z 从 1 起；开发迭代递增 z。普通本地构建和同一次失败构建重试不必反复改版本。
- 提升 w/x/y 或稳定晋级须用户已有明确指令，不因编译/测试成功自行晋级。
- `1.2.3 → 1.2.3.1 → 1.2.3.2 → 1.2.4` 有效。`1.2.3.2 → 1.2.3` 无效，不能通过删除 z 倒退。
- 提升 x 后 y 归零；提升 w 后 x/y 归零。稳定发布省略 z，下一轮开发 z 重新从 1 起。
- 有破坏旧存档/配置兼容的累计改动时，可以只升 z 继续开发，也可以经指令升 x；不能只升 y 发布为稳定版。对比基线是上一稳定版本，不只是最后一个开发提交。
- 标准发布顺序要求全局递增；如需并行维护旧分支，先明确分支/通道比较规则，不能悄悄用旧号发布。

## 晋级的证据

稳定晋级可以没有功能代码变化，但需要当前适用的测试证据、明确的稳定发布指令以及可追溯产物。若只改版本元数据，比较源文件和 JAR 条目后可复用仍适用的证据；仍核对最终元数据、哈希和依赖，不能声称重跑过全部测试。

允许已知且有依据证明无关的历史失败，须列用例、失败结果与无关依据；相关失败或根因未知不能包装成“无关”。用户完成的验收可以作为注明来源和范围的证据，Agent 不必重复用户排除的测试。

编号格式不是测试证明。迁入本协议前的历史三段版本保留原编号与产物，不追认全部稳定；设定有证据的过渡基线。发布渠道若区分稳定/开发，应保持历史可查，不能把无稳定版的项目默认为稳定。

## 修改本协议

维护者可直接指定新规则，无需继续遵循本模板的分段含义。记录生效点、示例、历史处理及跨规则比较方法；同步 PROJECT-CONFIG、AGENTS、构建元数据、依赖范围、发布说明和任何已存在的版本解析/比较工具。

用具体序列验证排序与晋级，不重新标号或覆盖历史 JAR。四段格式是否被目标平台正确解析要单独核对；平台行为不一定等于这里定义的比较器。
