# 本地交付与发布准备

默认输出可追溯的本地交付包。使用者可另外指定公开发布渠道或本地测试客户端清单；没有明确配置和任务授权时不上传或推断安装目标。本模板不提供部署工具或远程运维流程。

## 交付前

1. 按 [版本协议](VERSIONING.md) 确定版本，检查本 Mod 历史最大已发布版本、累计兼容性和稳定晋级指令。
2. 冻结源码状态和依赖，核对生成资源已更新；构建目标运行 JAR，区分 dev/sources/未重映射产物。
3. 读取 JAR 内元数据确认 modid、版本、MC/Loader/依赖范围及物理侧；检查资源、许可证/NOTICE、可选依赖和测试代码是否误入包。
4. 建立版本、文件名、大小、SHA-256、源码基线、变体和测试报告的对应关系。文件名仅供展示，元数据和字节才是核对依据。
5. 写 [发布说明](Templates/RELEASE-NOTES.md)：具体玩家变化、兼容/迁移注意、实际验证、已知问题。没有执行的检查不得填通过。

同版存在不同依赖变体时，显式记录各自条件、文件和哈希；不能让用户误装两个具有相同 modid 的变体。

## 交付与可追溯性

使用新版本的不可变文件名/目录，保留历史产物，不同内容不覆盖同版。可对同字节的失败传输重试；传输后重新核对大小与哈希。重新构建改变 ZIP 时间戳时，整包哈希变化不必然意味着代码变化，需要逐条目检查，仍不能覆盖已发布产物。

发布数据或本地清单若多人维护，先取得最新基线，在 Publish 认领内逐项合并并验证依赖，不用过期整份文件覆盖其他人的新条目。产物先存在且通过校验，再把版本索引指向它。

验证充分与用户允许发布是两个条件；用户已明确要求完成测试后发布时，完成相关检查即可继续，不重复索取相同授权。

## 可选的本地客户端持续更新

清单默认为空。若使用者明确启用：每次实际更新 Mod 后检查清单中客户端的真实版本隔离目录，按 modid 找到已安装项，保留配置，备份被替换的相关文件并核对候选。未安装不自动新增，不创建缺失的 mods 目录；新增依赖另按任务授权。

检查全部 JAR 元数据，避免旧版本与新版本并存；其他 Mod 和配置保持不变。运行中的实例不热替换，等用户退出或明确暂缓并记录。替换文件不授权启动或操作常用客户端。

回滚文件与回滚存档是不同事项。候选已写入世界后不能直接用旧 JAR 打开，须按既定迁移策略和世界副本确认。模板不安排任何定时安装或自动更新。

## 完成记录

写清交付版本和产物、实际执行范围、安装目标（如有）、保留的历史、未测事项与失败。稳定候选仅改版本元数据时说明证据复用依据，不把版本晋级写成新增功能。结束相关进程、提交选定文件、更新 CURRENT 并释放认领。
