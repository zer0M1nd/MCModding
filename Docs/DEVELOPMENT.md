# Mod 开发闭环

## 1. 把需求变成可验证行为

先说明玩家如何获得内容、如何使用、成功/失败会发生什么、成本如何变化、存档重开后应保留什么。阅读相关源码、API、配置和既有报告。移植先理解原版完整链路，联动先核实目标 Mod 的实际版本。

将范围写成 [功能规格](Templates/FEATURE-SPEC.md)：包括正常路径、边界、负例、客户端反馈、持久化、依赖和未包含内容。复杂任务按系统划分批次，不按“每一个物品”切成反复启停游戏的小任务。

报告的问题先按 [Bug 判定](BUG-POLICY.md) 分类。用户已要求修复时可继续调查、实现和验证；若只是询问或检查，不据此擅自加入功能或发布。

## 2. 建立基线和占用

使用 [协作协议](CONCURRENCY.md) 的可用工具，获得模块、共享文档及本轮实例所需认领。检查 Git 状态；记录目标分支/提交、未提交变更摘要、当前版本、依赖快照与配置。不要使用文件名推断正在运行的版本。

复现 Bug 时尽可能先取得失败基线；保留复现步骤、环境与结果。无法复现可继续源码分析，但要区分“实现风险”“已复现问题”“尚无证据”。不强行把所有报告归为已确认 Bug。

## 3. 完成一个可用系统

| 层面 | 完成条件 |
| --- | --- |
| 身份与生命周期 | 注册时机、稳定 ID、加载侧、初始化与卸载清理正确 |
| 玩家获得 | 配方、掉落、世界生成、进度或其他获取途径可达；创造列表按产品需求提供 |
| 业务规则 | 输入、成本、权限、容量、输出、失败反馈明确；模拟调用无副作用 |
| 保存与同步 | 完整数据保留、异常输入可处理、客户端接收真实权威状态 |
| 表现 | 语言、材质、模型、GUI、手册/配方展示、必要音效与动画完整 |
| 配置与联动 | 默认与显式覆盖区分；缺少可选 Mod 能加载；配置开关不会留下断链内容 |
| 扩展 | 标签、数据包、公开 API 与缓存重载支持符合承诺 |

先集中完成系统实现，再补足复杂分支与高风险行为的测试；不要求每个普通物品都新写专用测试。保留有效的既有测试，避免只验证“源码中有这个字符串”或照抄实现的断言。

数据生成代码与手工资源分目录；生成后审阅差分，避免同一路径覆盖手写资产。修改代码后验证真正加载的产物，不依赖旧进程自动更新类。

## 4. 调试顺序

1. 缩小触发条件：版本、安装组合、配置、游戏模式、维度、输入与时序。
2. 观察最先出现的有效异常或不变量破坏；后续级联错误不一定是根因。
3. 对照目标版本 API 与实际调用点，确定是产品错误、测试夹具、工具、依赖或需求变化。
4. 做最小且完整的修复；涉及共享 API 时认领全部被改模块，并核对旧调用者。
5. 验证原失败场景、合理反例、失败回滚和相关邻近功能。保留失败与修正记录。

禁止为全绿直接修改 golden、删失败用例或取消功能。确认夹具错误后可以修正夹具，记录原因并保持真实业务断言。

## 5. 分批验证与候选冻结

按 [三类测试](TESTING.md) 制定矩阵，收齐一批失败后集中修复，再回归该批及受影响范围。纯算法不必启动 GUI，视觉问题不能只做逻辑查询。用户限制测试时继续完成允许的工作并记录未测项。

冻结准备交付的 JAR、依赖清单、配置与 SHA-256。最终候选发生变化后，根据字节/源码差分判断哪些证据失效，补跑受影响用例。不能将候选 A 的测试结论直接贴到候选 B。

## 6. 交付与收尾

依据 [版本协议](VERSIONING.md) 编号，按 [交付规范](RELEASE.md) 导出真实 JAR 和具体更新说明。版本不变的普通本地重建不算新发布；已发布版本不能用不同内容覆盖。

更新模块 CURRENT、变化台账和报告，清楚写“已实现”“已验证”“未验证”。只提交本轮经审阅内容。退出自己启动的测试进程，完成交接并释放认领；被保留的现场继续有明确 owner。

交付说明包含：用户可见变化、版本/产物、实际执行的测试、已知失败与未测边界、是否进行了指定安装动作。不要用测试总数替代覆盖说明。
