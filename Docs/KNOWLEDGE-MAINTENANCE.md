# 知识与状态维护

将长期规则、产品规格、当前状态和运行证据分开。Agent 下次能从短入口继续工作，比把整段聊天复制进仓库更有用。

| 文件类型 | 维护方式 |
| --- | --- |
| AGENTS / 工作区规范 | 放当前有效、跨任务的要求；变更时更新关联入口，移除冲突描述 |
| PROJECT-CONFIG | 项目身份、技术栈、兼容边界、可覆盖政策；私密环境值不入库 |
| 模块 SPEC | 玩家可观察行为、系统边界与验收要求 |
| 模块 CURRENT / 全局 CURRENT-STATE | 当前版本/候选、已实现与已验证范围、未完成项、下一步及报告指针 |
| DECISION / MIGRATION-CHANGE | 为什么这样设计、改变了什么、影响谁、兼容和验证依据 |
| 测试报告 | 具体候选/环境/步骤/结果/证据，保持历史事实，不因新版本通过改写旧失败 |

## 使用历史对话

只有任务允许且资料可访问时检索相关对话。先找当前规则，再读影响当前决策的具体回合与附件。区分用户明确要求、Agent 建议、实际执行和未经证实的总结；失效附件/不可见内容写明缺口。

后续纠正优先于旧建议，但历史任务的一次授权不能无限扩展。查到“已完成”要追到对应产物、日期和范围；若当前源码或配置已改变，重新判断证据适用性。

输出通用知识时抽象触发条件、原因、防护和测试方法，不复制原始聊天、用户身份、设备路径或内部项目链接。与某个产品玩法绑定的特例不要变成所有 Mod 的硬规则。

## 控制文档体积

CURRENT 只保留最新可行动摘要；长日志、截图、运行数据放 Data，必要公开证据先脱敏后明确纳入。旧报告归档并保留引用，不把旧路径原样当可用现场。

结束任务时使用 [交接模板](Templates/HANDOFF.md)，确保能回答：正在做什么、哪些已完成、哪些没测、当前候选是什么、哪些资源仍占用、下一步如何继续。不要因清理文档删除唯一回归依据。

## 规则变更

记录变更依据与生效点，同步 AGENTS、专题和模板中的重复描述。版本协议尤其要同步示例和解析工具。人工认领与工具认领只能有一个状态真源。

定期检查相对链接、文档中不存在的工具命令、过时技术版本、未展开的模板字段，以及“全量通过”是否有证据。没有新变化或未解决疑虑时，不反复重跑相同验证。
