# 三类测试与证据规则

执行前先读取本文件、当前任务范围和模块状态。默认按风险完成必要隔离验证；用户明确“不测试”“不启动客户端”“仅服务端”时遵循限制，记录未测原因。**MC Pilot 操作真实客户端仍属于客户端测试。**

## 三种测试的定义

| 类型 | 定义与执行方法 | 能证明 | 不能替代 |
| --- | --- | --- | --- |
| 单元测试 | 在测试框架中检查隔离的算法、规则或组件，如 JUnit；不启动完整游戏世界 | 纯逻辑、解析、匹配、计算、异常输入、状态转换及边界 | 实际注册、完整 tick/事件链、专服类加载、真实网络与画面 |
| 服务端测试 | 在本地隔离的真实 Minecraft 权威逻辑环境中验证世界行为；用 GameTest、测试命令或独立测试 Mod 断言 | 注册、配方、库存/资源守恒、实体、权限、世界生命周期、持久化等；执行真实专服才覆盖其类加载与独立进程条件 | 客户端真实输入、GUI、渲染、音效；FakePlayer 也不等于联网玩家 |
| 客户端测试 | 启动有实际渲染的隔离客户端，执行真实玩家交互并观察同步、界面和画面/声音 | 实际输入路径、菜单、显示、模型、特效、音效以及客户端接收结果 | 只有客户端字段不能证明服务端权威状态；单人不能冒称专服或多人覆盖 |

编译、资源静态检查、JAR 哈希、字节一致、启动到主菜单是辅助检查，不是上述三类功能测试全部通过。性能、兼容、迁移是跨类别的测试目标，不另替代三种基本证据。

## 工具分工

- **MC Pilot**：默认客户端驱动，执行游戏内查询、移动、交互、输入、截图/录制。安装到真实隔离客户端；详见 [CLIENT-TOOLS](Testing/CLIENT-TOOLS.md)。
- **Forge GameTest**：验证世界逻辑与 tick 断言；不是 GUI 或图形测试工具。目标加载器不同则选其实际支持的测试框架。详见 [GAME-TEST](Testing/GAME-TEST.md)。
- **独立临时测试 Mod / 测试 source set**：覆盖专有 GUI、持久数据、同步或计数器，调用真实业务入口并观察结果。不能替业务写入预期输出。
- **电脑操作工具**：仅在启动器/系统对话框、接口缺失、输入问题或旧版本对照等必要环节使用；遵循当前可用工具的技能与接口说明。不能假定某个 MCP 或技能已经安装。
- **spark / JFR**：分析卡顿与资源消耗，记录本地 profile；详见 [PERFORMANCE](Testing/PERFORMANCE.md)。
- **图像/视频查看工具**：实际打开截图或检查录像片段。文件存在、Base64 返回成功、截图哈希正确都不等于已经审阅画面。

可按需安装测试辅助 Mod，记录版本、来源、哈希和安装侧；只放本轮隔离实例，不进入产品依赖/发行 JAR。工具失效记 `blocked`，不立即判定产品失败或通过。

## 选择环境

| 变更/场景 | 必要覆盖方向 |
| --- | --- |
| 纯算法、匹配、配置解析 | 单元正常/边界/反例；游戏生命周期有影响时追加运行测试 |
| 新方块/机器/物品机制 | 真实获得与使用、输入输出和失败、保存、客户端同步与相关表现 |
| 自动化/库存/流体/能量 | 真实能力接口、simulate 无副作用、实际接受量、满/空/拒绝、重复调用、掉落和重载 |
| 数据包/配方/标签 | 实际资源加载、重载、条件分支、制作结果与展示一致性 |
| 网络/权限/客户端类隔离 | 真实客户端连接本地隔离专服，合法/非法请求与双端结果；必要时两个玩家 |
| 视觉与输入 | 有渲染的客户端、实际 Screen 路径、不同缩放与视角、真实画面 |
| 保存格式/配置迁移 | 旧版本世界副本升级、首次加载、保存退出、再次加载，未知数据与显式配置保留 |
| 可选联动/渲染优化 | 最小环境、依赖存在/缺失、声明支持的版本组合；不宣称未测版本兼容 |
| 性能 | 固定场景的基线与候选、相同操作/预热/采样时长、profile 和实际体验证据 |

普通交互可用客户端加集成服务器；专服/网络特有行为必须用独立专服。多人可见性、所有权和观察者问题需真实相应玩家，不能用一次单客户端测试概括。

## 一轮联合测试的流程

1. 建立唯一 run ID，认领模块与 `test:<run-id>`，检查 Git 和旧测试进度。
2. 冻结候选并建立 [环境与结果记录](Templates/TEST-MANIFEST.md)：MC/加载器/Java、产品和测试 Mod 版本及 SHA、配置、数据包、世界种子、图形设置、用例和命令。
3. 使用独立目录、世界、账号别名和空闲端口。只复用合法的库/assets；不要复制个人账户凭据和整份常用实例。控制接口仅本机访问。
4. 接入自检：确认进入世界、读实际库存、打开普通容器、做一次可恢复槽位往返并验证双端守恒、查看截图；验证测试框架确实执行并能报告失败。
5. 按“准备 → 正式动作 → 服务端断言 → 客户端同步 → 必要画面/音效 → 清理”运行。命令可准备场景，正式验收不能用命令直接生成目标结果。
6. 等待具体条件和合理 tick/时间预算，保存原始请求、响应与日志。超时可能动作已执行，先查状态再重试，避免二次扣费或重复产出。
7. 先收集整批问题再集中修复；重新冻结候选，回归受影响场景和必要反例。
8. 正常保存退出，确认本轮进程结束，释放输入与临时强加载，整理报告和认领。

建议实际运行时创建以下目录，当前模板不预装实例：

```text
Data/Verification/<run-id>/
  client/  dedicated/  requests/  responses/
  screenshots/  videos/  profiles/
  manifest.json  results.json
Docs/Verification/<run-id>/PLAN.md
Docs/Verification/<run-id>/REPORT.md
```

## 合并两端测试与复用证据

同轮取得真实服务端断言、客户端同步和必要画面，可同时记录 `server-logic`、`client-sync`、`client-visual`，无需机械重复独立服务端测试。每种覆盖都必须有实际证据。只运行 GameTest 或读客户端 NBT 不满足这个条件。

同一场景的截图、断言与重试不能简单相加为独立通过用例。记录用例数、断言数、证据帧数各自含义。复用旧证据时核对产物、依赖、配置、行为链及工具是否仍适用，写明复用理由和范围。

## 结果与完成标准

结果可为 `pass / fail / blocked / not-run / deferred-by-user / not-applicable`，每种非通过状态写原因。没有执行不填 pass；没有适用性依据不填 not-applicable。保留失败历史，用最新有效结果更新当前结论。

报告包含实际环境、候选哈希、覆盖、观察、证据路径、未测项和下一步。最终运行包未变可复用证据；若仅版本元数据变更，说明逐条目差分，不声称在稳定包上重跑过游戏。

测试通过范围必须匹配功能声明。与本次无关的已知失败可单列，但根因未知不能被轻易排除。运行游戏需要用户暂缓时，交付应写“实现完成，客户端未验证”。
