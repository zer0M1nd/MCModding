# 低版本向高版本迁移

## 默认目标

迁移的目标是让旧版核心玩法在目标版本中完整、可用、可维护，并保留关键风格和玩家认知。理解旧源码的意图后按现代 API 重写；不以逐行翻译、复制老旧底层机制或逐像素一致为默认目标。

优先使用新版原生注册、寻路、战斗、交互、物品、标签、粒子、字体和界面机制。专有机制继续自定义；“有原生同名类”不代表它语义相同。迁移前比较前置条件、时序、失败行为与扩展性。

完整实现所承诺系统：获取、使用、消耗、反馈、保存、网络和界面。仅注册物品、做出材质或让手册页面出现，不算功能移植完成。

## 建立功能与差异台账

固定原作者版本和来源，分清原版、维护分支、整合包改版。其他分支可供修复和技术参考，不能顺带引入其配方门槛、平衡数值和依赖。

按玩家功能组织：旧行为及依据 → 目标行为 → 现代实现 → 差异类别 → 兼容处理 → 需要的测试 → 当前状态。类别采用：增强/削弱、适配新版、新机制、追加联动、Bug 修复、其他。跨 Mod 修改记在受到影响的功能下，注明提供方。

使用 [迁移变化模板](Templates/MIGRATION-CHANGE.md)。没有核对过的内容写“待核对”，不能直接写“未实现”或“已保留”。

## 通用映射检查

| 旧机制 | 迁移目标与容易遗漏的点 |
| --- | --- |
| 数字 ID / metadata / OreDictionary | 稳定命名空间 ID、BlockState、目标版本标签；元数据曾编码的状态逐项映射 |
| 旧物品与原版重复 | 复用现代原版等价物，更新配方/掉落/图标；已有注册 ID 仍按兼容策略迁移 |
| 硬编码物品/树种白名单 | 标签与数据驱动规则，验证第三方加入和数据重载 |
| 老库存/能量/流体接口 | 目标平台能力或传输 API；方向、null 查询、模拟/提交、实际接受量、生命周期全部核对 |
| 旧 AI 任务 | 现代 Goal/导航/目标条件，保留专属工作约束；重配置不重复累加任务 |
| 旧维度数字和坐标哨兵 | 维度资源键、完整位置；现代负高度有效，不使用 Y=-1 代替“无位置” |
| 旧数据字段/NBT | 可演进 schema、缺省与异常值策略、未知数据保留、幂等迁移 |
| 旧包与客户端类引用 | 目标网络 API、方向、主线程处理、长度/索引/权限限制；专服可独立类加载 |
| 旧渲染/OpenGL 即时调用 | 目标版本的模型、缓冲、矩阵和渲染阶段，恢复图形状态，验证光影与原生路径 |
| 旧 GUI/字体/手册 | 现代 Screen/Menu/文本组件、缩放、换行、翻译；保留信息层级与操作反馈 |
| 旧世界生成 | 目标数据驱动注册与生物群系方案；区分新生成区块和已保存区块，禁止未授权回填 |
| 旧存储与静态缓存 | 按世界/维度/生命周期隔离，避免跨世界泄漏；重载、退出、失效时清理 |

不同版本和加载器的 API、资源格式及物品数据机制不通用。不要把 Forge 1.20.1 示例当作 NeoForge/Fabric 或所有新版的固定写法。实际签名以目标依赖源码为准。

## 兼容性是显式承诺

迁移玩法与迁移旧 Minecraft 存档是不同任务。默认不承诺跨 Minecraft 大版本直接打开老世界；必须写清支持的新项目历史版本、配置格式、API 与资源包范围。若需要旧存档导入，单独设计与测试转换流程。

对于已经承诺支持的存档/配置，稳定 ID、字段、默认值和数据意义都不能随意改。用世界副本验证：升级前状态 → 升级后首次加载 → 正常保存退出 → 再次加载。未知注册项不要静默丢弃，迁移应可诊断且重复执行不会重复发物或扣费。

不兼容的累计变更要按 [版本协议](VERSIONING.md) 处理；改版本号不会自动修复存档。重开旧 JAR 也不是可靠回退，新版本可能已修改数据。

## 资源与对照

代码许可、素材许可和分发许可分别核对。反编译可辅助理解，但其输出可能失真；可疑分支结合字节码或旧版实机验证。不要将阅读参考资料等同于允许整包复制。

视觉以整体风格、关键形体和反馈为重点；普通现代字体不要求逐行断行一致。特殊模型、复杂 GUI、动画和效果需要时做新旧同场景对照。素材字节相同只能证明来源相同，不能证明在新渲染管线中显示正确。
